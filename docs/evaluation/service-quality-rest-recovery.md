# 曲の途中で休符になった歌唱の再判定

2026-09-07、PR #17の `28856aa` に対する追加修正。前半は聴けるが後半が崩れるという試聴結果を受け、任意のBasic Pitch単音推定で、音がある区間まで休符として落ちる問題を調べた。UI・YIN・テンポ推定・モデル重み・公開基盤は変更していない。既存要件を維持する不具合修正で、新しい受け入れ条件の達成は主張しない。

## 原因と採用範囲

元の単音DPは最大の一鍵の活動を休符の対立候補にする。声の音程が隣接半音に分散すると、一鍵ずつは弱いため、長い休符に負ける場合があった。モデルはその区間で音高と発音の証拠を出しており、記譜の丸め以前に音符が欠けていた。

元のDPで得た全音符を保ち、その音符に挟まれた100ms以上の休符だけを再確認する。二つ目のDPは最大活動鍵と隣接半音の活動を足して上限1とし、休符側の観測費用だけへ使う。これは有声の支持量であり、校正済みの音声確率ではない。各音高の観測費用・遷移費用は変えない。

追加できるのは休符に全体が収まり、100ms以上続き、開始の35ms前〜100ms後に同音/隣接半音のonset≥.5がある候補だけ。隣接半音へ連続して揺れても新しい発音証拠がなければ一音へまとめ、区間全体の活動が多い音高を選ぶ。明確な再発音は分ける。既存音符を短くしたり、別の音高へ置き換えたりせず、冒頭/末尾の未確定区間を補わない。曲名・正解譜面・YINを入力へ追加しない。

## 比較して採用しなかった案

[比較候補JSON](service-quality-rest-candidates.json)は同じキャッシュ済みモデル活動による比較。10曲を等重み、VocaditoのA1/A2は各曲内で平均、記譜は手動120 BPM。試作時のpolyphase再標本化なので、後述の本番ブラウザ数値と混ぜない。全て既使用の回帰素材で、結果を見ながら候補を比較した。新規holdoutの成功とは呼ばない。

|候補|音高+開始F1|譜面F1|同一曲の譜面F1の最大悪化|判断|
|---|---:|---:|---:|---|
|修正前|58.86%|57.52%|—|比較元|
|休符からの遷移に発音証拠を使う|59.54%|58.17%|10.91pt|対象の欠落が直らず不採用|
|同上、隣接半音の発音も使う|59.55%|58.17%|10.91pt|不採用|

単一の平均値を最大化せず、既存の音符、冒頭/末尾、短音の回帰を重視した。100ms未満の欠落や曲全体が弱い場合は補えない。無条件の隙間埋めや正解曲への吸着にはしていない。

## 本番ブラウザから原音を再解析した結果

[今回の全10曲JSON](service-quality-rest-results.json)と[修正前JSON](service-quality-browser-results.json)。同一音源・参照注釈のSHA256一致、標準YINの全曲の音符指標不変を確認。Docker ChromiumでWAVを48kHz monoへデコードし、本番Worker内の再標本化・推論・単音化、同じScoreの記譜/ピアノまで再実行した。

音符F1はMIDI完全一致・開始100ms以内の最大1対1照合。終了込みはさらに `max(100ms,参照音長20%)` 以内。譜面は手動120 BPMで原音時計へ戻す。移調・時刻合わせ・音源のテンポ変更をしない。F0正解率ではない。

標準YINとの比較では、Vocadito 24の記譜前、PJS010の譜面などで今回も劣る。任意の別推定として残す。自動テンポは10曲×2方式で0/20、不確実の仮120を自動成功に数えない。原テンポ80/120/180の区別は維持しており、JSONには手動公式BPMの診断も別にある。

出典・権利条件・取得手順は[Vocadito](vocadito-sources.md)と[PJS](vocal-score-sources.md)。音源・原譜面・個別音符列は公開結果に含めない。

## 合成・実録音・ブラウザを分けた確認

- モデル活動の回帰テストを先に追加し、修正前に欠落3ケースが失敗、修正後に全9ケース成功。隣接半音への分散、再発音の有無、冒頭/末尾の保護、入力不変、既存の無声・時間境界を確認。関連Worker境界と合わせて15/15、型検査・Vite build、Chromiumの再採譜/中止2/2が成功。既存VexFlowの大きいchunk警告は継続。
- キャッシュ済みの合成音6ケースは修正前と音符列・記譜前/後指標が同一。100ms半音変化と持続倍音は成功を維持するが、弱い基音の100msオクターブ跳躍等は依然失敗している。「6ケース全て正確」とは扱わない。新実装と固定試作の出力は公開10件・合成6件・ローカル実録音1件で一致した。
- 本人の歌唱と母音は同じM4Aを既にDockerで変換したWAVとして本番UIへ再入力。新旧の標準推定、母音の別推定はScore再生音符・WAVとも同一。歌唱の別推定は15→17発音、全5小節・省略0。最初の9発音は同一で、WAVも再生時刻4.750秒までは同一。後半で休符扱いだった2音を追加できたが、独立正解注釈がないため正解率とは呼ばない。
- 同じScoreからピアノWAV・全小節のカタカナPNGを再生成。PNGを目視し、有限の非無音WAV・クリップ0・外部要求0・pageerror0を確認。本人録音や生成物はローカルだけへ保存。M4A直接入力の成功とは扱わず、今回の修正版の本人による最終試聴と実演は未確認。

本番ブラウザの公開10曲では別推定0.90〜2.54秒（8〜38.736秒入力、取得・再標本化・Worker起動・二段DP込み、ファイルdecodeは別）。localhostの単回結果で実端末の保証ではない。

上限60秒の合成PCMを配布用にminifyした本番API/Workerで追加計測し、別推定3.445秒、標準解析23.616秒。新しいページで各1回、並行の解析なし。入力不変・Worker終了後active 0・pageerror 0を確認した。[測定条件とソース/ビルドハッシュ](service-quality-rest-performance.json)。これは合成音の速度確認であり、実声精度・実端末・ピークメモリの証拠ではない。従来の10秒入力全経路5秒目標も未達のまま。

新しい端末APIを使わない単音decoderの修正のため、今回のブラウザ操作は関連Chromiumに限定。前段のWebKitや全UIの証拠は測定時のハッシュで保持し、今回再実行したとは扱わない。iPhone Safari/Android Chromeの実機マイク・codec・物理騒音・複数声・最終聴感、ピークメモリ、全自動BPM/拍子/調/短音/音程の完全復元は未達または未検証。mainへのマージ・本番公開・Issueクローズは行っていない。

```bash
docker compose -f docker-compose.test.yml run --rm --no-deps browser \
  node --experimental-strip-types scripts/benchmark-service-quality.ts \
  --include-final --include-pjs --output output/rest-recovery-NEW.json
```
