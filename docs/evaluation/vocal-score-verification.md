# 複数テンポの単独歌唱・公式譜面との比較

比較元は `48b48d73fdf603f7746e70508bbe2df3d9ae9008`。利用者の「ぷつぷつ・音階のズレを直し、異なるテンポの無料ボーカル3種類と正解譜面でも確認する」という依頼に対応した。REQ-001〜015を維持、REQ-016追加、削除・保留なし。

**採用したのは、楽譜への丸めが不要な再打鍵を作る不具合の修正。音高検出と自動テンポの改善案は比較で採用条件を満たさず、未達のまま残した。** 元PCM、Hz/cents、音符推定、Vite/TypeScript/公開基盤は維持する。今回の結果を「鼻歌を正確に全自動採譜できる」とは評価していない。

## 採用した変更

同じ音の間に20msの別音が入る例では、別音だけが16分グリッドの丸めで消え、前後の同音を二度打鍵していた。省略前の音符列が連続し、前後が同じMIDI、丸め後の端点も接するときだけ1イベントへまとめた。実際の隙間、同音再発音、省略された同音再発音が途中にある場合は結合しない。元の短音を省略した件数はそのまま表示する。

提供歌唱は同じ原フレーム、同じ仮120 BPM、同じピアノ音源で、譜面再生の打鍵数が23→19になった。派生音符29個と記譜省略6個は変わらない。母音録音は5→5打鍵。これは不要な再打鍵の減少であり、正解音符数との一致ではない。低音への飛びや有声判定の空白は残る。提供音声・個別フレーム・WAV・譜面画像はすべてローカルのignored `output/` にだけ保存した。

## 音源と過調整対策

[PJS公式配布](https://sites.google.com/site/shinnosuketakamichi/research-topics/pjs_corpus)の単独歌唱を使用。作成者はJunya Koguchi / Shinnosuke Takamichi、CC BY-SA 4.0。選定規則、許諾、固定ZIP/ファイルハッシュは[取得資料](vocal-score-sources.md)を参照。

解析前に譜面メタデータのみで80/120/180 BPMから1曲ずつ固定し、タイムストレッチも結果による曲の差し替えも行わなかった。`pjs010` と `pjs040` で比較し、`pjs017` は本番候補を固定してから初めて解析した。その後の本番変更はない。3曲は同じPJS歌手であり、話者をまたいだ汎化検証ではない。

公式MusicXMLは作曲上の音高・発音/終了・BPMの基準で、実演されたF0の正解ラベルではない。歌唱の揺れや子音、発音の遅れも差へ含まれる。本番解析器へはPCMだけを渡し、基準音符・曲名・BPMを入力しない。時刻シフト、DTW、移調を使わず、生成譜面の相対時刻にはScore自身のoriginを足して原音時計へ戻した。

## 比較して採用しなかった方式

実験コード・詳細出力はローカルに保持。以下は調整/回帰集合での比較であり、未使用の実録音に対する改善実績ではない。調整は最終確認曲を見る前に終了した。

| 方式 | 観測と不採用理由 |
| --- | --- |
| 波形候補の強い連続性優先 | 提供歌唱の飛びは減るが、予備12合成PCM条件で本物の短い音を消す。強い設定では新たな誤音が最大10時点、短音保持失敗4条件。弱い設定は主症状の改善不足 |
| 40ms窓で短い低音を確認してから補正 | 最長低音確認60/80msの設定は168条件の本物100ms歌声跳躍で3/6条件の回帰、17/32フレームの新たな誤音。40ms設定は回帰0だが提供歌唱は変わらず |
| 不確実/無声区間を短窓で回復 | 閾値0.95・20ms支持ではpjs040の音符F1が43.75%→46.15%だが、pjs010は50.79%→50.00%。提供歌唱は29→31音と分割増。音を増やすだけでは改善しない |
| 60msの話声窓と歌声窓を併用 | pjs010の音符F1は54.29%へ上がるが、pjs040は40.00%へ低下。提供歌唱も32音へ増える |
| 発音時刻中心の頑健なテンポ候補 | 既知30テンポ条件の近似候補は23→28件だが、実歌唱2曲では採用条件を満たさず、180 BPM曲の候補も外れる。実際の使用BPM/譜面の改善根拠が不足 |
| 周期的ビブラート成分だけを音符推定用コピーから除去 | 0.7秒窓、4〜8 Hz、R²≥0.7等の制限でpjs010の音符F1は50.79%→56.14%。前後半の周期・振幅・位相一致も要求すると52.46%へ縮小。不規則な合成カーブ200フレーム中12にも補正が残り、pjs040/提供2録音は不変。主要な改善と誤補正抑制の両立が不十分 |

周期除去の最後の候補では、既知216条件の音符列一致/100ms短音保持は212→212、実際の解析器へ通す合成PCM24条件は24→24、追加トリル24条件の列一致は18→18。新たな回帰はなかったが、元から残る失敗も解消していない。この成功だけで不規則な実歌唱への安全性を保証せず、本番へ入れなかった。

## 検証の区分と未検証

- **合成・unit**: Docker Node24で86/86成功。不要な再打鍵の反例は修正前に失敗、修正後に成功。実休符、同音再発音、複数省略、入力不変を含む。独立レビューでも先頭/末尾・小節跨ぎ等38の境界ケースが成功。評価helperは最大1対1照合、オクターブ違い、終了時刻許容、倍半分BPMを9テストで確認。
- **実録音**: 固定PJS3曲を元の速度で実解析し、提供2録音も既存の原フレームから再生成。公式譜面のタイ/休符/半音を独立に読み直して全音符・時刻が一致した。元のF0正解精度、未知話者の完全採譜は未検証。
- **ブラウザ成果物**: 同じピアノ音源と本番schedulerで、3曲の基準・修正前・修正後、提供歌唱の前後をローカルWAV/カタカナ付きPNGへ生成。基準側は元の32分音符と先頭休符を保ち、再生は公式音符時刻から直接予約。アプリ側は本番のScoreを使う。最初の比較画像生成は32分音価を拒否して停止し、基準側の表示だけを修正した。本番の16分制限は変えていない。
- **ブラウザ操作とビルド**: Docker Chromiumの関連8/8成功（譜面再生、停止、テンポ変更、失敗後の再試行、ページ送り、375/1280pxの収まり）。上記11組のPNG/WAV生成テストも成功し、3曲の基準/修正後と提供歌唱の画像を目視した。ホストのCodex内ブラウザでローカル比較ページを開き、3曲・前後・試聴操作の表示を確認。実マイクは使っていない。TypeScript/Vite build成功、既存VexFlow約728kB chunk警告は継続。評価runnerはコンテナ内だけのNode型定義でstrict型確認、取得Pythonはmypy strict/ruff確認済み。
- **性能**: 3曲の修正後解析＋音符化＋記譜は約7.30/6.32/3.38秒（録音18/16/8秒）。Docker Node24/Linux arm64の単回で他検証も並行しており、改善率や実端末性能を主張しない。本番の追加処理は音符走査内の定数処理のみ。既存の60秒上限と4小節描画を維持。
- **未検証**: 実機マイク、iPhone Safari/Android Chrome、物理雑音、OS音声中断、低速端末/ピークメモリ、修正音の利用者最終試聴と譜面からの実演。合成マイクやDocker Chromiumで代替しない。F0本番コードが不変なので既存384条件の性能/F0行列は今回再計測していない。解析器を変更する場合に再実行する。

本番コードと評価runnerを独立レビューし、仮120を自動テンポ成功と混同する集計名を修正した。音符が多く欠落する問題、正確な自動BPM/拍の復元、自由テンポ・弱起・調/拍子の復元は未達。UIの見た目で音程精度を達成扱いにせず、mainマージ・本番公開・Issue #13クローズは行わない。

## 再現

先に[固定3曲の取得](vocal-score-sources.md)を実行する。比較元を固定するため、既存作業ツリーを上書きせずignored専用ディレクトリへ展開する。

```sh
mkdir -p output/pjs-evaluation/baseline
git archive 48b48d73fdf603f7746e70508bbe2df3d9ae9008 src | tar -x -C output/pjs-evaluation/baseline
docker compose -f docker-compose.test.yml run --rm --no-deps unit \
  node --experimental-strip-types scripts/benchmark-vocal-score.ts \
  --baseline-src output/pjs-evaluation/baseline/src --include-holdout
```

候補比較中は `--include-holdout` を省略し、80/180 BPMの2曲だけを使う。一度結果を見た最終確認曲は次回の未使用データとして扱わない。runnerはローカルの `comparison.json` と曲別 `before.json` / `after.json` を出力し、元音声・譜面を公開せず集計だけを報告する。
